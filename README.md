# readme-lint

Сверяет `README.md` C++-проекта с его кодом и выводит расхождения в формате компилятора:

```
README.md:90: ошибка: сигнатура com.example.store.setItems: в README 'as', в share/store.xml 's' [dbus]
```

Работает офлайн: источники правды берутся из самого репозитория (файлы, исходники, `build-deps.lst`,
D-Bus XML), сеть и LLM не нужны. Подходит для запуска в CI.

## Использование

```
readme-lint [ключи] [КАТАЛОГ]
```

| Ключ | Назначение |
|---|---|
| `КАТАЛОГ` | корень проекта, по умолчанию текущий каталог |
| `-f`, `--file ФАЙЛ` | проверяемый README, путь от корня проекта, по умолчанию `README.md` |
| `-I`, `--include КАТ` | системный include-каталог для внешних имён, можно несколько; по умолчанию `/usr/include` и `/usr/local/include` |
| `--dump` | вывести найденные в README блоки кода и inline-код, без проверки |
| `-V`, `--version` | версия программы |
| `-h`, `--help` | справка |

Код возврата: `0` ошибок нет (предупреждения возможны), `1` найдены ошибки, `2` ошибка запуска.

## Правила

| Правило | Что берётся из README | С чем сверяется |
|---|---|---|
| `markdown` | блоки кода | закрывающее ограждение есть, иначе остаток файла рендерится как код |
| `names` | пути, имена файлов и идентификаторы в `` `...` `` | `git ls-files`, код проекта, системные заголовки |
| `deps` | пакеты в командах `apt install` | `build-deps.lst`, `debian/control`, CI |
| `dbus` | вызовы `busctl call` и `dbus-send` | XML-описания интерфейсов, таблицы sd-bus, код |
| `options` | ключи командной строки программы | `getopt`, `struct option`, `add_options`, разбор аргументов в коде |
| `snippets` | блоки ` ```cpp ` | компилятор |

Реализованы правила `markdown`, `names`, `deps`, `dbus` и `options`, остальные в планах.

### Разбор markdown

Поддерживается подмножество CommonMark, достаточное для правил: блоки в ```` ``` ```` и `~~~`
(длиной от 3, с любым отступом, в том числе внутри списков), inline-код из любого числа обратных
кавычек, в том числе с переносом на следующую строку абзаца, экранирование `` \` ``. Блоки с отступом
4 пробела не выделяются. Разбор сверен с markdown-it-py на 92 README: число блоков и содержимое
inline-кода совпадают.

### Правило names

Проверяет inline-код, который похож на путь или имя из кода. Остальное (обычные слова, команды,
значения) не трогает: ложное срабатывание хуже пропуска.

| Что в README | Когда проверяется | Где ищется | Не найдено |
|---|---|---|---|
| путь `src/app/server.cpp`, `src/session/`, `src/app/server.*` | есть `/` и известное расширение или первый сегмент существует в проекте | файлы проекта (`git ls-files`, вне git обход каталога): точно, от каталога README, по концу пути, glob; затем системные include-каталоги | ошибка |
| имя файла `metrcs.cpp` | без `/`, известное расширение | имена файлов проекта и системных заголовков | предупреждение |
| имя `safe_invoke()`, `m_cache`, `OrderParser`, `ns::Type::method` | есть `_`, `::`, `()` или camelCase; `std::` пропускается | слова в коде проекта и в именах файлов без расширения, затем в системных заголовках | ошибка |
| ЗАГЛАВНОЕ имя `PATH_TO_DATA` | как имя | там же | предупреждение (часто переменная окружения или CMake) |

Кодом считаются исходники, CMake, XML, YANG, JSON, `build-deps.lst`, скрипты с `#!`.
Документация (`.md`, `.puml`, `.txt`) не считается: устаревшая диаграмма не должна подтверждать
устаревший README. Вне git каталоги `build*`, `cmake-build-*`, `.git`, `.idea`, `.vscode`, `.cache` не входят в проект.
Каждое имя сообщается один раз, на первом упоминании.

### Исключения

Имена, которые не нужно проверять (примеры, ключи конфигурации, внешние программы), перечисляются
в `.readme-lint-ignore` в корне проекта, по одному на строку:

```
# примеры из документации
my_sax
safe_invoke()
```

Строка сравнивается и с текстом inline-кода, и с проверяемым именем.

### Правило deps

Сверяет пакеты из команд `apt install` / `apt-get install` README с источниками сборочных
зависимостей проекта:

| Источник | Что берётся | Полный список |
|---|---|---|
| `build-deps.lst` | `имя[=версия]` через пробел или по строке, строки с `$` пропускаются | да |
| `debian/control` | поля `Build-Depends*`, версия только из `(= V)` | да |
| `.github/workflows/*.yml` | пакеты из `apt-get install` | нет, в CI бывают служебные пакеты |

Команды ищутся в блоках `bash`, `sh`, `shell`, `console`, `zsh` и без языка, а также в inline-коде.
Строки с `\` в конце склеиваются, `sudo` и опции пропускаются, `&&`, `;`, `|`, `<`, `#` обрывают
команду. Установка собранного пакета (`./tool.deb`) и аргументы с подстановками не проверяются.

| Расхождение | Уровень |
|---|---|
| версия пакета в README отличается от зафиксированной в источнике | ошибка |
| пакета из команды нет ни в одном источнике | предупреждение |
| пакета из полного источника нет в команде, которая покрывает не меньше половины источника | предупреждение |

Команда, ни один пакет которой не входит в источники, считается установкой зависимостей для запуска
и не проверяется.

### Правило dbus

Находит во всех строках README (в блоках кода, inline-коде и обычном тексте) вызовы методов:

- `busctl [опции] call СЕРВИС ОБЪЕКТ ИНТЕРФЕЙС МЕТОД [СИГНАТУРА АРГУМЕНТЫ...]`;
- `dbus-send --print-reply` или `--type=method_call ... ОБЪЕКТ ИНТЕРФЕЙС.МЕТОД тип:значение...`,
  сигнатура вычисляется из аргументов (`string:` даёт `s`, `array:string:` даёт `as`,
  `dict:string:int32:` даёт `a{si}`, `variant:` даёт `v`).

`busctl tree`, `introspect`, `emit` и сигналы `dbus-send` не проверяются. Строки с `\` в конце
склеиваются, кавычки снимаются, команды с плейсхолдерами (`<service>`) пропускаются.

Описание метода ищется по порядку:

| Источник | Что проверяется | Не совпало |
|---|---|---|
| XML-описание интерфейса в проекте (любой `.xml` с `<interface>`) | метод есть в интерфейсе, сигнатура входных аргументов | ошибка |
| системное описание `/usr/share/dbus-1/interfaces/ИНТЕРФЕЙС.xml` | то же | ошибка |
| таблица sd-bus в коде: `SD_BUS_METHOD`, `..._WITH_NAMES`, `..._WITH_ARGS` | сигнатура метода с тем же именем | ошибка |
| ничего не найдено | имя метода встречается в коде проекта | предупреждение |

Интерфейсы `org.freedesktop.*` без описания не проверяются. Если интерфейс задан в коде без явной
сигнатуры (например, `registerMethod` в sdbus-c++), проверяется только имя метода. Исключения из
`.readme-lint-ignore` сравниваются с `МЕТОД` и `ИНТЕРФЕЙС.МЕТОД`.

### Правило options

Ключи программы в коде (каталоги `test*`, `bench*`, `example*`, `sample*`, `demo*`, `fuzz*`,
`third_party`, `vendor`, `external`, `3rdparty` не учитываются):

| Источник | Пример | Объявляет ключ |
|---|---|---|
| строка `getopt`, `getopt_long` | `"ho:c::"` | да |
| массив `struct option` | `{"output", required_argument, NULL, 'o'}`, даёт пару `-o`/`--output` | да |
| `add_options()` (boost, cxxopts) | `("help,h", ...)` | да |
| литерал в строке со сравнением или регистрацией в файле, разбирающем аргументы | `arg == "--dump"`, `add_flag("--quiet")`, `add_argument('-v', '--verbose')` | да |
| любой другой литерал | `"-4"` | только известен |

Ключи в README:

- в командах программы проекта: имя из `add_executable`/`project`, файлов в `bin/` или каталога
  стоит в начале строки или inline-кода (после `$`, `sudo`, `VAR=...`) или после `&&`, `;`, `|`;
- в начале строки: строка таблицы, пункт списка, строка справки `-h, --help  текст`, `**-b** _size_`;
- в inline-коде только из ключей и плейсхолдеров: `--dump`, `-f ФАЙЛ`.

Ключи чужих программ (`apt install -y`, `cmake --build`) не берутся.

| Расхождение | Уровень |
|---|---|
| ключ из README не встречается в коде | ошибка |
| объявленный ключ не описан в README (пара `-c, --check` одной строкой; `--help` и `--version` не требуются) | предупреждение |

О неописанных ключах сообщается, только если README описывает не меньше двух объявленных ключей
и не меньше трети из них: иначе README не документирует CLI, и список был бы шумом.

## Сборка

```
apt install build-essential cmake libfmt-dev libgtest-dev libgmock-dev
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
```

DEB-пакет: `cd build && cpack -G DEB`.
